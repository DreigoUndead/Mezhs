# Integration runtime — current behavior

This is the runtime behavior implemented on the `integration-architecture-v2` branch; see [architecture](../../docs/architecture.md) for owners and [the plan](../implemented/integration-architecture-v2/plan.md) for acceptance criteria.

- One integration instance per configured connection; immutable per-chat prompt contexts. Core owns chats, local messages, remote continuation mappings, history and persistence. Provider-generated outgoing IDs are persisted before submission, and reply parent IDs are retained. Existing local IDs, chat links, files and history are preserved.
- `ChatContext.GetHistoryAsync` selects chronologically ordered Core messages across connections by nullable limit/offset and oldest/newest direction, without providers opening SQLite directly.
- Integrations return a best-known executed/current/selected model. A warning appears when an explicit non-default requested model differs from the same-connection reply's returned model, without retry or automatic reselection; a selected-model fallback is not a provider verification.
- The direct integration model/login/diagnostic contract replaces legacy capability modules. `AllowFiles` gates input attachments; output files are handled without a capability flag. The API base remains lightweight and can expose the ordinary HttpClient-backed typed HTTP adapter; the local-model base remains a placeholder.
- Browser integration owns connection `limits.maxParallel` and `limits.minInterval`; local ChatId sends remain serialized. Browser account integrations reuse the shared authenticated Electron host, per-chat windows and account session; guest contexts are ephemeral. Agent retains/releases its chat context across shell waits. Cancellation never automatically replays an uncertain send.
- Browser integrations expose `StopAsync(chatId, messageId)` against the already-running Electron operation. On prompt-token cancellation the Electron transport requests one bounded provider stop **before** local operation cancellation/context retirement. The stop result distinguishes `NotActive`, `Unsupported`, `Attempted` and `ProviderConfirmed`; no provider-confirmed outcome is claimed without observed acknowledgement. ChatGPT Account uses an AbortSignal on its signed POST/stream and state polling; ChatGPT Guest, Grok and Gemini attempt their existing per-window stop controls. These are best-effort attempts, not evidence that remote generation stopped; ambiguous prompts are not retried. Scoped stop never creates a new authenticated host or changes admission Waiting.
- ChatGPT Guest, Gemini Guest and Grok Account retain existing DOM behavior pending a separately scoped provider-protocol refactor.
- `IntegrationHttpClient` supplies typed GET/POST/PATCH endpoint execution and C# JSON/SSE/NDJSON interpretation through composition. `ApiIntegrationBase` exposes the ordinary `HttpClient` adapter and `BrowserHttpExecutor` composes the same typed mechanism over the existing authenticated Electron browser transport. The Electron provider operation permits bounded same-origin `/backend-api/` requests, with provider-owned credentials, cookies and integrity observations. Methods dispatch once: uncertain mutation submissions and cancellations are **not** automatically replayed. Stream contents are buffered within a 16 MiB response bound, with byte-progress reports, then interpreted in C#; this is not a new public incremental-text stream API.
- ChatGPT Account model discovery now uses this typed Electron GET and C# picker normalization; native model and thinking-effort identifiers remain unchanged. ChatGPT prompt submission, account-specific Sentinel/conduit preparation and reply recovery still use the established provider JS path, not the generic typed operation. This is not a claim of live typed HTTP mutation submission against ChatGPT.

This file records observed implementation behavior, not independent review or final release approval.
