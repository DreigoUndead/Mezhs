# Safe rich UI rendering for model replies
ID: rich-model-ui-rendering
Level: **High-risk** — provider text can contain SVG, MDX-like expressions, state declarations, and actions that must remain inert unless deliberately recognized as safe data and invoked by the user.

## Goal and evidence
The shared renderer shows native SVG and a ChatGPT DIL question as literal markup instead of a diagram and selectable radio options with a Confirm button. Make these **two supported subsets** render for any provider through `src/Mezhs.Web.Lib`, preserving ordinary Markdown, existing rich layout/chart support, and literal code examples.

First seek the **actual raw model-message text** for one SVG diagram and one Grill Me question, and use it as a checked-in test fixture. If only screenshots are available, add explicitly labelled representative fixtures reconstructed from them and validate against real payloads when available. Inspect how `remark-mdx` represents those nodes and locations; adapt the bounded subset to evidence, never screenshot-specific text substitutions.

**Not in scope:** a general DIL/MDX runtime; executing `{@body}` as JavaScript; arbitrary hooks, callbacks, loops beyond the already supported restricted templates, SVG hyperlinks/assets/animation, new model/provider transports, or a new chat-send subsystem.

## Existing ownership and architectural decision
- `MarkdownContent.tsx` calls `expandRichTemplates`, then `react-markdown` with `remark-gfm`, `remark-mdx` and `remarkRichMarkup`. `RichMarkup.tsx` maps a static tag/property allowlist to React elements; `RichExpression.ts` owns a restricted data evaluator/loop expander, including fence/inline-code shielding. `RichChart.tsx` already renders bounded declarative data. **Reuse/repair this pipeline; do not compile MDX or add a second HTML renderer.**
- `MezhsChatApp.tsx` currently renders message bodies directly and owns the normal `submit()` flow, chat/connection/model selection, `useConversationPending`, `useConversationDrafts`, attachments and selection epochs. `ChatSurface.tsx` / `ChatTranscript` render the same `MarkdownContent`, currently without a send callback. `Mezhs.Agent.Web/src/App.tsx` uses `ChatTranscript` but submits *agent executions* via `/v1/executions`, not ordinary `ChatProvider.sendMessage`. Treat that transcript as **read-only** for model-authored submission actions in this task.
- Prefer a **small typed renderer contract** between parsed DIL descriptors, message-local React controls, and an optional host-owned action callback. One active send mechanism and one renderer; no provider-specific replacements, global event bus, dynamic components/evaluation, or speculative generic DIL framework.

## Implementation plan

### 1. Establish parser and trust boundaries
1. Reproduce both raw fixtures and characterize MDX node types/offsets, especially `{@body ...}`, JSX attributes, nested SVG tags, and template literal click handlers. Check current `expandRichTemplates` behavior on these samples; its whole-string expansion, attribute interpolation, and error fallback must not consume or partially rewrite interactive syntax.
2. Parse supported constructs **as untrusted syntax data**, using existing Markdown/MDX AST locations and a deliberately restricted Acorn AST where necessary. Recognize only the specified grammar; never pass raw declarations/handlers through to React DOM props. Do not use `eval`, `Function`, dynamic imports, `dangerouslySetInnerHTML`, HTML parsing for execution, model JavaScript callbacks, or a generic AST interpreter.
3. Preserve fenced/inline code and escaped markup as literal examples, including when they contain `{@body}`, loops, SVG, or buttons. Reject malformed/unrecognized directives as visible escaped source; recover at the smallest practical subtree/block so one bad element does not erase adjacent valid text/layout/chart content.
4. Keep per-message parsing bounded (source length, AST nesting, nodes, string lengths and generated output); continue existing template-loop limits. Parse once per content revision where practical, but do not introduce a second persistent cache or global registry.

### 2. Static SVG (React nodes only)
1. Within an allowed `<svg>` subtree, support a **minimal drawing allowlist** needed by the captured diagram, starting with `svg`, `g`, `rect`, `path`, `line`, `polyline`, `polygon`, `circle`, `ellipse`, `text` and `tspan`; add an element only against a demonstrated fixture. Descendant SVG `text` is SVG text, while `<text>` outside SVG stays the existing MEŽS rich-text component. Do not change the meaning of regular Markdown text.
2. Map verified SVG tags/attributes to real React SVG elements. Accept only plain, validated, bounded presentation values (for example `viewBox`, numeric geometry, path `d` / `points`, `fill` / `stroke`, limited stroke/font/text alignment and `role` / `aria-label`). Support responsive width such as `100%`, and constrain height and viewBox dimensions. Translate standard SVG attribute spelling to React properties explicitly; do not spread unvalidated attributes or let HTML/SVG namespace mix.
3. Reject **the complete unsafe SVG subtree** rather than silently dropping suspicious fields when it has unknown elements, executable/event props (`on*`), `script`, `foreignObject`, `image`, `use`, `href` / `xlink:href`, `style`, `url(...)` paint/CSS, filters, animation, external resources, or arbitrary namespaces. React-escape label text; do not parse SVG descendants as new DIL controls. Bound node count, nesting, path bytes, geometry and output size to avoid browser hangs; the failing SVG remains readable as escaped source.
4. Render diagram labels as real selectable SVG text. Ensure useful accessibility labelling, responsive containment, and no overflow of the conversation pane. Do not attempt a general-purpose SVG sanitizer or support features that require external loading.

### 3. Restricted declarative DIL controls
1. Support the screenshot's **one-state question grammar**, not arbitrary body code: `{@body const [choice,setChoice] = DIL.useState("B")}` (also normal whitespace/newline variants), `<radio-group value={choice} onChange={setChoice}>` with `<radio value="A">...` / `"B"` options, and a `<button>` whose `onClick` is a restricted arrow calling `GenUI.issueNewTurn` with one bounded template literal interpolating `${choice}`. The fixture must establish actual spacing and interpolation; the intended supported interpolation is precisely the declared state identifier. Use a restricted AST match for the declaration, literal default, field binding, setter reference, and one `GenUI.issueNewTurn` call with a bounded literal/template string. Never evaluate a model-authored function.
2. Convert syntax to **typed declarative descriptions**. Exact known binding names must resolve to a valid declaration and valid option values. No arbitrary identifiers, property access, computed expressions, expressions with side effects, additional statements/hooks, network calls, DOM operations, or method aliases. Do not expand `RichExpression`'s general arithmetic/object grammar to evaluate actions. A malformed or partially unsupported form is inert, never an enabled action.
3. Implement state in a normal, stable React component boundary scoped to **one message instance** (chat + message ID); hooks must not execute conditionally, in the parser, or inside `react-markdown` render callbacks. Persist a choice through harmless rerenders/streaming updates of that message, reset when the message/conversation identity changes, and avoid sharing state across multiple questions/messages.
4. Use native accessible labelled radio inputs and a `type="button"` Confirm control, with keyboard/focus/checked state and explicit disabled state when no valid action or host callback exists. No implicit form submission. Render simple Markdown text in radio labels through the existing safe Markdown path, without letting labels register additional actions. Provide a visible explanation when a supported question cannot submit.

### 4. Host-owned submission bridge
1. Add an **optional, narrow** `onIssueNewTurn(content: string)` callback at the shared message-rendering boundary, supplied **per eligible assistant message**. Keep action validation and text interpolation in the shared renderer; keep authority to send in the host. The renderer must not call a provider, inspect global chat state, switch conversations, or submit during rendering/effects.
2. In `MezhsChatApp`, make the composer and rich button call **one existing dispatch path** with explicit content/options. Preserve the current provider, selected chat ID, selected model, category rules for new chats, pending/busy gate, offline checks, errors, selection epoch, polling and response updates. A rich action is eligible only while its source assistant message belongs to the **currently displayed chat** and is complete; guard stale closures/chat switching and connection mismatch before sending. Do not create or redirect to another chat on a stale click.
3. Rich actions send `content` with **no attached files** and do not read, clear, mutate or restore the current draft or pending uploads. Composer submission continues to own its usual draft/attachments behavior. Both paths share the same synchronous in-flight lock (`startSend` or equivalent) to block rapid double-clicks and concurrent composer sends; re-enable only when the normal pending state allows it. If the message disappears, changes identity, is not an eligible assistant reply, the API is offline, or the chat is busy, the button is disabled/inert.
4. Do not wire `ChatTranscript` to the Agent Web `/v1/executions` API by accident: absent callback means read-only/disabled controls there. If a future host opts in, it must explicitly implement its own authorized submission semantics.

### 5. Styling and graceful fallback
Keep scoped styling in `src/Mezhs.Web.Lib/src/markdown.css`: SVG containment, radio groups, labels, focus-visible and disabled/busy buttons. Respect existing themes, mobile layout, Markdown spacing, charts and scrolling. Unsupported DIL or unsafe SVG must remain readable/escaped with safe surrounding content still rendered, not transform into active-looking controls or crash the transcript.

## Security invariants
- **Model text is never executable code.** Acorn/MDX are syntax parsers only; all React element types, props, content, state references and action kinds come from host-owned allowlists.
- **Only intentional clicks can send.** An allowed action has no effect during render, hydration, streaming, polling, message updates, or focus; all dispatch goes through the host's existing submission guards.
- **One message, one state and destination.** No cross-message choice leaks, no stale callback sending into a newly selected chat or different connection, and no hidden draft/upload side effects.
- **Fail closed and locally.** Invalid AST/props or resource limits never mount unsafe SVG or handlers and do not break independent valid Markdown/rich content.

## Verification matrix (implementation stage)
1. **Parser and regression:** Use `node --test tests/agent-web-rich-formatting.test.cjs` plus new raw-fixture tests. Assert ordinary GFM, links, fenced/inline code, existing loop expansion, `box`/`row`/`grid`, `Chart` and DIL `<text>` remain intact. Cover SVG text namespace collisions, MDX flow vs inline markup, malformed directive isolation and the existing RichExpression shielding/preprocessing.
2. **SVG positive/negative:** Assert a real React `<svg>` tree (including `<text>` labels and valid geometry) instead of escaped tags. Reject/event-test `on*` variants, `script`, `foreignObject`, `image`, `use`, `href`, `xlink:href`, `style`, mixed-case/encoded `url(...)`, namespace tricks, malicious values, extreme node counts/depth/path/coordinates and malformed markup. Confirm adjacent safe content survives.
3. **DIL action safety:** Cover default B and changed A with exact interpolated outgoing string, accessible checked radio/keyboard behavior, invalid/mismatched setter/state, unsupported `{@body}` statements, prototype/constructor/globalThis access, calls other than `GenUI.issueNewTurn`, injection through radio labels/template values, malformed template literals, and no dispatch on mount/rerender/streaming. Assert unsupported handlers cannot reach DOM event props.
4. **Browser/React interaction:** SSR markup tests alone **cannot** prove click behavior. Add focused React DOM event tests (existing browser tooling if present; otherwise the smallest viable DOM test harness), including rapid double click, busy/offline states, async rejection, rerenders, multiple questions, chat changes and stale replies.
5. **Host integration:** Verify `MezhsChatApp` sends via the active provider/selected chat/model with **no attached files**, preserves draft and pending uploads on both success and failure, shares composer in-flight guards, and respects connection changes. Verify `ChatTranscript` / Agent Web stays safely read-only without the optional callback; ensure user, command-result and incomplete assistant messages cannot send.
6. **Developer/independent stages:** Run relevant TypeScript builds, existing UI/architecture tests, and a real browser interaction check. Document commands, exit codes and limitations against the exact tested commit. Refresh codegraph only if dependency edges change. High-risk independent code review **precedes** independent final testing.

## Acceptance criteria
- [ ] The captured OpenTelemetry diagram renders as responsive, accessible, real SVG with selectable labels.
- [ ] The captured Grill Me question renders native radio choices and Confirm; B is selected initially, choosing A changes the **single** submitted new-turn text.
- [ ] Unsupported JavaScript/DIL and unsafe SVG remain inert/escaped; no code execution, implicit sends or injected DOM handlers/resources.
- [ ] State and send destination stay within the correct message/conversation even under rerenders, switches, double-clicks and failures.
- [ ] The user's composer draft and attachments remain untouched by rich actions; composer and action sends share one guarded dispatch mechanism.
- [ ] Existing rich Markdown/layout/chart behavior and both host integrations remain compatible; regression, security and interaction checks are recorded for the exact SHA.
